# Gajaeway 1.0: Rust Core Architecture Design

**Status**: Draft for 0.x → 1.0 strategic planning  
**Date**: 2026-10-26  
**Scope**: No code changes to `~/.gajaeway`, no PR merge until approved

---

## Executive Summary

Gajaeway's current TypeScript architecture (0.x) handles session/agent orchestration, multi-platform chat delivery, and durable work scheduling, but exhibits reliability and operational debt that prevent 1.0 stability:

- **State corruption on lane death**: Work lanes dying mid-operation leave zombie processes, orphaned git worktrees, and database rows in inconsistent states
- **Cross-session interop chaos**: Handoffs, posts, and memory access across session/broker boundaries lack centralized guard rails and atomicity
- **Manual update/migration burden**: Each version bump requires explicit `gajaeway migrate`, schema cranking, and operator recovery procedures
- **Storage leaks**: Memory corpus, delivery ledgers, and work artifacts accumulate without bounded expiry or compaction
- **Process supervision gaps**: Adapters and broker children can disappear or hang without coordinated recovery

This document compares three architectural approaches for 1.0: **(A) Full Rust rewrite**, **(B) Hybrid core (Rust daemon + TS adapters), and (C) TS + structural cleanup**. Each option includes cost, risk, migration path, and cutover strategy.

**Recommendation**: **Option B (Hybrid Core)** is the optimal path—it isolates the most failure-prone components (work lane coordination, durability, process supervision) into Rust while preserving existing TS adapter investment and allowing gradual migration.

## Part 1: Current Architecture Analysis

### 1.1 TS Architecture Overview

Gajaeway 0.x is organized as a Bun TypeScript monorepo:

| Component | Responsibility | Lines | Notes |
|-----------|---|---|---|
| `@gajae-gateway/gateway` | Core daemon; state/ledgers, session relay, delivery, memory | ~3K (gateway/) + 50K+ (orchestrator/) | Bun binary; SQLite backend; manages broker relay and work lanes |
| `@gajae-gateway/protocol` | Versioned NDJSON frames, origins, verb catalogue | ~1K | Zero dependencies; used by CLI and adapters |
| `@gajae-gateway/sdk` | Client for gateway socket/stdio; session binding | ~1K | Node-compatible; used by CLI |
| Adapters (Discord/Slack/Telegram) | Platform ingress/delivery; typing, reactions, presence | ~2K each | Bun binaries; stateless relay clients to gateway |
| `@gajae-gateway/cli` | Owner commands: daemon control, migration, status | ~2K | Bun binary; uses protocol+SDK |
| Admin console | Web dashboard (if enabled) | ~1K | Separate binary; read-only ops interface |

**Critical subsystems:**
- **Orchestrator** (`packages/gateway/src/orchestrator/`): Work lane admission, session/broker relay, git integration, GJC child process spawning
- **Store** (`packages/gateway/src/store/`): SQLite schema (19 migrations), multi-owner table access control, transaction serialization
- **Delivery ledger** (`packages/gateway/src/delivery/`): At-least-once outbound delivery state machine, expiry, redelivery
- **Memory corpus** (`packages/gateway/src/memory/`, `packages/gateway/src/persona/`): Git-backed Markdown tree, bootstrap safety, redaction

### 1.2 Observed Failure Modes (0.x Reality)

#### A. Lane Death + State Corruption

**Symptom**: A work lane (long-running task/session) exits abnormally, leaving behind:
- Running child processes (GJC, git, build tools) as zombies or hung until reaper timeout
- Locked git worktree in semi-committed state
- Database rows (work_attempts, lane_reports) marked `pending` but will never complete
- Socket connections to broker in limbo

**Root causes**:
1. No unified supervision: lane jobs are spawned in isolation with only exit-watch recovery
2. Process reaping relies on file-polling (see `process-reaper.ts`); git subcommands can spawn grandchildren that inherit descriptors
3. Work lane state machine (work-lane.ts, 3900+ lines) has competing exit paths: terminal evidence, sentinel checks, broker reconciliation
4. No atomic transaction boundary across: broker API call, database update, child process cleanup, git operation

**Current mitigation**: Lane governor sweep retires "unproven" jobs after 30 min, but already-committed database/filesystem/git state is abandoned.

#### B. Zombie Running States + Cross-Session Interop Chaos

**Symptom**: Sessions report broker unavailable or work stalling despite broker running; adapters lose connection to gateway and desiccate state.

**Root causes**:
1. **Broken broker health probing**: Broker liveness check (broker-liveness.ts, ~200 lines) uses process.pid polling and file discovery. Restarted broker with same PID passes health, but GJC clients inside are new process with fresh state.
2. **No coordinated session rebinding**: When broker restarts, in-flight sessions are stranded. Rebind logic (rebind.ts, ~300 lines) exists but is not automatically triggered on broker health transitions.
3. **Adapter-to-gateway handshake lacks atomic safety**: Adapters open connections without coordinated lease acquisition. If gateway crashes mid-turn, adapter may retry the same DM, causing duplicate delivery or race.
4. **Handoff/post routing** (handoff.ts, ~300 lines) is built on convention: parsing regex in reply text, no atomic registry of active handoff targets, loose coupling between source and target sessions.

#### C. Manual Migration + Schema Churn

**Symptom**: Each version bump (0.1.0 → 0.2.0) requires:
1. User runs `gajaeway migrate` (or it fails silently)
2. Schema version bumped; new migration entry added to migrations.ts
3. Operator must capture baseline before upgrade, handle rollback on failure
4. `gajaeway up` prompts for credentials again even if config.json exists

**Root causes**:
1. Schema migrations live in TypeScript code (migrations.ts, 19 versions, 350+ lines); each version is a separate closure with manual INSERT
2. No embedded schema history or automatic schema-to-code sync
3. Credentials stored in plaintext `.env` or separate files; no versioned config schema
4. Monitors, channel policies, and broker identity are all mutable, creating 3-way merge conflicts between user edits, migrations, and daemon state

#### D. Storage Leaks + Unbounded Growth

**Symptom**: Gateway database and memory corpus grow without cleanup:
- Delivery ledger accumulates `expired` or `confirmed` rows indefinitely
- Memory files grow to 10+ MB with no compaction or archival
- Work lane git worktrees are never pruned (can be 100s MB each)
- Broker sessions in memory accumulate unless manually purged

**Root causes**:
1. Delivery expiry is hardcoded (24 hours) with no batched cleanup; old rows are checked on each delivery sweep but not deleted
2. Memory compaction is manual and offline (separate operator runbook); no background expiry or archive-to-tar
3. Git worktree pruning is not automated; lanes retire but their repos stay on disk
4. Broker session list is unbounded; old sessions from abandoned users are never cleaned up

### 1.3 Extracted 1.0 Requirements

From failure modes, 1.0 must guarantee:

| Requirement | Failure(s) Addressed | Acceptance Criteria |
|---|---|---|
| **Atomic lane lifecycle** | A, B | Lane job transitions (created → running → terminal) and cleanup (kill child, mark DB, remove git) must be atomic or crash-recovery-safe |
| **Durable work queue with idempotency** | A, B | All broker operations (create, prompt, close) serialized through durable queue with idempotent keys; broker restart does not replay or lose pending work |
| **Unified process supervision** | A, B | Single supervisor (daemon responsibility) that owns spawning, health monitoring, and forceful termination of all children; no async reaping assumptions |
| **Automatic session rebinding on broker health transitions** | B | When broker becomes unavailable and then recovers, in-flight sessions automatically re-attach without user intervention |
| **Bounded storage with automatic expiry** | D | Delivery ledger, memory corpus, work artifacts all have explicit retention policies and background compaction; no growth without bounds |
| **Versioned, zero-manual-migration config** | C | Schema, config, credentials, and monitors are versioned together; upgrades are auto-applied with rollback-safe snapshots |
| **Atomic multi-session handoff/post** | B | Routing targets registered durably; post and handoff operations are transactional across source and target |

## Part 2: Three Migration Options

### Option A: Full Rust Rewrite

**Scope**: Rewrite gateway daemon, orchestrator, delivery, memory, and store entirely in Rust. Keep protocol and CLI as-is (TS/protocol is stable). Adapters migrate gradually.

**Architecture**:
```
┌─────────────────────────────────────────────────────┐
│          Gajaeway 1.0 (Rust Core)                    │
│ ┌─────────────────────────────────────────────────┐  │
│ │ Daemon (Rust)                                    │  │
│ │ - Work queue + state machine                     │  │
│ │ - Process supervisor                             │  │
│ │ - SQLite manager with migrations                │  │
│ │ - Session relay + memory bootstrap              │  │
│ │ - Delivery ledger + expiry                       │  │
│ │ - Adapter socket listener                        │  │
│ └─────────────────────────────────────────────────┘  │
├─────────────────────────────────────────────────────┤
│ CLI + Protocol (TS, unchanged)                       │
├─────────────────────────────────────────────────────┤
│ Adapters (Gradual TS → Rust migration)              │
│ - Phase 1: TS adapters (stateless relay clients)    │
│ - Phase 2: Rust adapters (as needed)                │
└─────────────────────────────────────────────────────┘
```

**Pros**:
- **Strongest guarantees**: Memory safety, concurrency safety, zero-cost abstraction eliminate entire classes of bugs (zombie processes, race conditions, segfaults)
- **Performance**: Rust binaries are ~5-10× smaller, faster startup, lower memory footprint
- **Long-term maintainability**: Rust ownership model and type system enforce correctness at compile time; no accidental async/await pitfalls or process leaks

**Cons**:
- **Highest dev cost**: ~8–12 person-weeks to rewrite 50K+ lines of TS orchestrator/store code; Rust learning curve for existing TS team
- **Longest timeline**: 3–6 months of development + testing before 1.0 release
- **Dependency migration risk**: Rust SQLite (rusqlite/sqlx), async runtime (tokio), protocol serialization (serde) must be fully validated; no incremental migration path
- **Adapter ecosystem reset**: Existing TS adapters must be replaced; third-party adapter authors have no legacy support
- **Rollback complexity**: No version running both TS and Rust core in parallel; if issues found late, entire rewrite must be deferred

**Cost breakdown**:
- Core daemon rewrite: 5 weeks (orchestrator 2w, store 1w, memory 0.5w, delivery 0.5w, supervisor 1w)
- Store/schema/migration: 2 weeks (versioned schema, automatic migration, fixture data)
- Testing (unit, e2e, chaos): 2 weeks
- Adapter migration (if chosen): 2+ weeks per adapter
- **Total**: 9–14 weeks for 1.0 release

**Migration path**:
1. Develop Rust daemon in parallel branch; full test coverage against existing protocol and adapters
2. Snapshot 0.19 as "legacy" branch; freeze new features
3. Release 1.0.0 with Rust daemon; TS protocol and adapters stable
4. Provide `gajaeway migrate-data` tool to import 0.19 databases
5. Gradual adapter rewrite in Rust or maintain TS adapters indefinitely

**Data migration**:
- SQLite schema and data exported to JSON, re-imported under Rust schema (handles 19→1 consolidation)
- Memory corpus exported as markdown, re-initialized under Rust memory system
- Broker session data preserved but re-bound to new authority
- No user-visible downtime if snapshot/restore procedure is automated

**Cutover**:
- Non-destructive: old 0.19 database kept; Rust daemon creates new `.1.0.db` side-by-side
- Validation phase: both daemons run in read-only mode against separate databases; data consistency verified
- Atomic switchover: rename `.1.0.db` to `gateway.db`, restart adapters pointing to new daemon
- Rollback: revert daemon binary, restart with old database

### Option B: Hybrid Core (Recommended)

**Scope**: Rewrite work lane orchestrator, process supervisor, and durability guarantees in Rust. Keep delivery, memory bootstrap, and persona session relay in TS (simpler, stable). Adapters stay TS; no migration needed.

**Architecture**:
```
┌──────────────────────────────────────────────────────┐
│          Gajaeway 1.0 Hybrid                          │
│ ┌──────────────────────────────────────────────────┐  │
│ │ Daemon (Rust Core)                                │  │
│ │ - Work queue + durable state machine              │  │
│ │ - Lane supervisor + process reaper                │  │
│ │ - SQLite with auto-migration (core + bindings)   │  │
│ │ - Leader election / multi-daemon safety          │  │
│ │ ┌────────────────────────────────────────────┐   │  │
│ │ │ IPC boundary                                │   │  │
│ │ └────────────────────────────────────────────┘   │  │
│ │ TS Relay Runtime (existing 0.x)                   │  │
│ │ - Session relay + broker connection mgmt         │  │
│ │ - Delivery ledger (move to expiry + cleanup)     │  │
│ │ - Memory bootstrap + redaction                   │  │
│ │ - Persona state machine                          │  │
│ └──────────────────────────────────────────────────┘  │
├──────────────────────────────────────────────────────┤
│ CLI + Protocol (TS, unchanged)                        │
├──────────────────────────────────────────────────────┤
│ Adapters (TS, stateless clients)                      │
└──────────────────────────────────────────────────────┘
```

**Pros**:
- **Minimal rewrite scope**: ~2000 lines of Rust (supervisor, work queue, durable state) vs. 50K lines total
- **Fast 1.0 delivery**: 4–6 weeks to shipping; Rust core can be developed in parallel while 0.x continues
- **Incremental adoption**: TS components remain proven; no all-or-nothing migration risk
- **Adapter stability**: Existing TS adapters run unchanged; no third-party ecosystem disruption
- **Fallback path**: If Rust core has issues, revert to pure TS+cleanup (Option C) without abandoning whole effort
- **Team onboarding**: Smaller Rust learning curve; TS team can focus on their domain

**Cons**:
- **IPC complexity**: Rust core and TS relay must communicate via socket/JSON; potential latency, serialization overhead, and coordination bugs at boundary
- **Partial blame assignment**: When failures occur, unclear if root cause is Rust or TS layer; debugging distributed system harder than monolith
- **Dual schema responsibility**: Rust owns durability schema (work_attempts, lane_reports, broker_authority); TS owns session/delivery state. Schema migration must coordinate both.
- **Delivery ledger split responsibility**: Expiry logic moves from TS daemon to Rust supervisor; TS retains ledger model but Rust enforces cleanup. Coupling risk.

**Cost breakdown**:
- Rust supervisor + work queue: 2 weeks
- IPC + relay integration (TS side): 1 week
- SQLite schema consolidation (Rust): 1 week
- Testing + chaos validation: 1.5 weeks
- **Total**: 5.5 weeks for 1.0 release (vs. 9–14 for Option A)

**Migration path**:
1. Develop Rust supervisor as sidecar process; IPC via named socket to TS daemon (phase 1)
2. In 1.0.0: TS daemon spawns Rust supervisor as internal component; IPC is localhost Unix socket
3. After 1.0.x stabilization: consider moving more subsystems to Rust (delivery, memory) as separate phases
4. TS adapters unaffected; can be gradually rewritten after 1.0.0 is stable

**Data migration**:
- Rust supervisor reads existing SQLite schema (v19); co-existence phase handles both old and new tables
- Durable state (work_attempts, lane_reports) moved to Rust; TS continues to manage delivery and session state
- Broker authority (currently tiny, single row) moved to Rust as ownership signal
- Memory and persona data stay in TS; no migration needed

**Cutover**:
- Non-breaking: 0.19 → 1.0.0 is gradual. 1.0.0-rc releases use hybrid; Rust core validates against existing TS data
- Backward compatible: TS daemon can still read Rust schema; lane jobs completed by Rust supervisor are visible to TS delivery/session logic
- Rollback: Disable Rust supervisor; TS daemon falls back to lane-governor sweep (0.x behavior)
- Zero-downtime: Adapters stay connected to TS daemon; restart Rust supervisor without losing state

### Option C: TypeScript + Structural Cleanup

**Scope**: Keep all code in TypeScript. Refactor to address failure modes:
- Unify process supervision (centralize in lane-governor)
- Add idempotent work queue with broker reconciliation
- Implement bounded storage expiry
- Consolidate schema + config versioning
- Improve broker health probing and rebinding

**Architecture** (same as current, but cleaner):
```
┌─────────────────────────────────────────────────────┐
│          Gajaeway 1.0 (TS, Refactored)              │
│ ┌─────────────────────────────────────────────────┐  │
│ │ Daemon (Bun/TS)                                  │  │
│ │ - Unified process supervisor                     │  │
│ │ - Durable work queue (SQLite-backed)             │  │
│ │ - Auto-expiry for storage (delivery, memory)    │  │
│ │ - Coordinated broker rebinding                   │  │
│ │ - Atomic session handoff/post                    │  │
│ └─────────────────────────────────────────────────┘  │
├─────────────────────────────────────────────────────┤
│ CLI + Protocol (TS, unchanged)                       │
├─────────────────────────────────────────────────────┤
│ Adapters (TS, stateless clients)                     │
└─────────────────────────────────────────────────────┘
```

**Pros**:
- **Lowest dev cost**: 3–4 weeks of refactoring existing code; no language switch, team stays in TS
- **Fastest 1.0 release**: Could ship within 6 weeks (parallel to 0.19 maintenance)
- **Minimal risk**: No new dependencies, no ecosystem changes, no integration surprises
- **Good-enough for 1.0**: Addresses all stated failure modes (lane death, state corruption, zombie processes, storage leaks) without Rust safety guarantees
- **Team velocity**: TS team knows codebase intimately; refactor can be surgical

**Cons**:
- **No safety guarantees**: Rust prevents entire categories of bugs (memory leaks, race conditions, zombie processes); TS requires discipline and testing
- **Technical debt remains**: Async/await footguns, implicit process spawning, implicit state mutation all still possible
- **Long-term liability**: 50K+ lines of TS orchestrator code remain high-risk; future maintainers inherit cognitive load
- **Performance ceiling**: TS is slower than Rust; adapters may still timeout under load if not careful
- **Not a strategic fix**: 1.0 works, but 2.0 would still likely need Rust core to exceed current reliability ceiling

**Cost breakdown**:
- Process supervisor consolidation: 1 week
- Durable work queue (SQLite-backed): 1 week
- Storage expiry + compaction: 0.5 weeks
- Broker health + rebinding overhaul: 0.5 weeks
- Atomic handoff/post: 0.5 weeks
- Testing: 1 week
- **Total**: 4.5 weeks for 1.0 release

**Migration path**:
1. Branch from 0.19; freeze feature work
2. Refactor in-place: supervisor, work queue, expiry, schema versioning
3. Release 1.0.0 with same codebase, now more robust
4. Maintain indefinitely or plan Rust migration for 2.0 if new failure modes emerge

**Data migration**:
- In-place SQLite schema evolution (no new migrations needed beyond consolidation)
- Config/credentials/monitors versioned in single file; auto-upgrading loader
- No export/import step; existing databases continue to work

**Cutover**:
- Drop-in replacement for 0.19: same binaries, same protocol, same database
- Validation: existing test suite passes; no data loss
- Rollback: revert binary; old TS daemon still understands same schema
- Zero-downtime: Adapters stay connected; restart daemon cleanly

## Part 4: Recommended Path (Option B)

**Decision**: **Hybrid Core (Rust supervisor + TS relay)** offers the best risk/reward for 1.0.

**Rationale**:

1. **Tier-1 reliability for the tier-1 failure mode**: Work lane death and state corruption are the strongest pain points. Isolating them in Rust supervisor (idempotent state machine, atomic process supervision, durable queue) fixes the most frequent outages without rewriting everything.

2. **Proven architecture**: IPC between TS relay and Rust supervisor is a well-established pattern (e.g., Electron main/renderer). The boundary is narrow (work queue, lane health, process reaping) and easy to test in isolation.

3. **Fastest 1.0 delivery**: 5–6 weeks vs. 9–14 weeks (Option A) vs. 3–4 weeks (Option C). Option C saves 1–2 weeks but leaves architectural debt. Option B trades 1–2 weeks for solving the problem comprehensively.

4. **Graceful fallback**: If Rust supervisor has issues, fall back to Option C (pure TS+cleanup) without sunk cost. If Option C has issues, cannot easily adopt Rust later without wholesale migration.

5. **Team comfort**: Small Rust component (2000 lines) is learnable for TS team. Large Rust rewrite (50K lines) raises project risk and schedule uncertainty.

6. **Incremental path to full Rust**: After 1.0.0 stabilizes, move delivery, memory, and persona relay to Rust in separate 1.1–1.2 releases. Each phase small and testable.

## Part 5: Option B Detailed Design

### 5.1 Rust Supervisor Component

**Responsibilities**:
- Own work lane lifecycle: create, run, status, abort, retire
- Own process supervision: spawn GJC/git/build children, monitor health, forceful termination
- Own durable work queue: idempotent broker operation tracking
- Own lane state machine: entry/exit logic, atomicity guarantees

**Scope** (~2000 lines Rust):
```
gajaeway-supervisor/
  src/
    main.rs              # CLI entry, Bun interop
    supervisor.rs        # Core state machine (500 lines)
    work-queue.rs        # Durable queue (300 lines)
    process-reaper.rs    # Unified supervision (300 lines)
    ipc.rs               # TS relay IPC protocol (200 lines)
    store.rs             # SQLite accessor (300 lines)
    errors.rs            # Error types (100 lines)
  tests/                 # Unit + chaos tests (400 lines)
```

**IPC Protocol** (via Unix socket):
```jsonl
# TS → Rust: Create work lane
{"method": "lane.create", "id": "uuid", "workName": "task-123", "command": ["gjc", ...], "cwd": "/path"}
{"result": {"laneKey": "work-...", "jobId": "lanejob-..."}}

# Rust → TS: Lane status update
{"event": "lane.status", "laneKey": "work-...", "state": "running", "pid": 1234}

# TS → Rust: Get lane status
{"method": "lane.status", "id": "uuid", "laneKey": "work-..."}
{"result": {"state": "running", "exitCode": null, "childPids": [1234, 1235]}}

# TS → Rust: Abort lane
{"method": "lane.abort", "id": "uuid", "laneKey": "work-...", "reason": "user_cancel"}
{"result": {"aborted": true, "childTerminated": true}}
```

**State Machine** (simplified):
```
[CREATED]
  ↓
[RUNNING] ← supervisor monitors children, collects exit code
  ├→ [TERMINAL_SUCCESS] (all children exited 0, db updated, git cleaned)
  ├→ [TERMINAL_FAILED] (exit non-0, attempt reconciliation with broker)
  ├→ [TERMINAL_INTERRUPTED] (user abort, force-kill children)
  └→ [CRASHED] (crash before terminal state reached; broker reconciliation on recovery)

Transition invariants:
- RUNNING → TERMINAL: children must be dead before DB commit
- Any → CRASHED: supervisor crash during RUNNING leaves DB in "unproven" state
- CRASHED → recovery: on restart, supervisor reads "unproven" lanes, reconciles with broker result
```

**Durability guarantees**:
- All lane state changes written to SQLite before IPC reply to TS relay
- Work queue (broker operations) logged before issue; idempotent keys prevent double-submission
- Process cleanup (kill, git rm) is best-effort; if supervisor crashes mid-cleanup, recovery treats lane as unproven and retries cleanup

### 5.2 TS Relay Runtime Refactoring

**Responsibilities** (same as 0.x, but delegating lane work to Rust):
- Session/broker relay: open bidirectional stream to GJC broker
- Delivery ledger: durably track outbound messages, mark confirmed/expired
- Memory bootstrap: serve bounded session-start context
- Persona state machine: handle user interaction, generate replies

**Changes**:
1. Replace `lane-governor` sweep with Rust supervisor IPC
2. Simplify `work-lane.ts` to ~200 lines (create via IPC, poll status, handle completion callbacks)
3. Add auto-expiry for delivery ledger (background cleanup job, not critical path)
4. Add auto-expiry for memory corpus (optional, off by default for 1.0; on in 1.1)
5. Improve broker rebinding (on health transition, re-attach all sessions via IPC request to Rust supervisor for status)

**Key files touched**:
- `orchestrator/lane-governor.ts`: 30K → 5K (delegate sweep to Rust)
- `orchestrator/work-lane.ts`: 3900 → 200 lines (thin IPC wrapper)
- `store/open-work.ts`: Add supervisor sync on startup
- `delivery/delivery.ts`: Add configurable expiry sweep
- `server/server.ts`: Add broker rebinding trigger

### 5.3 SQLite Schema Evolution

**Current**: 19 ad-hoc migrations in TS closures.

**1.0 target**: Consolidate to versioned schema file; Rust supervisor auto-applies.

```
schema/
  v1.schema.sql        # All tables at version 1
  v1.down.sql          # Rollback (if needed)
  migrations.rs        # Rust executor
```

**Ownership split**:
- **Rust owns**: `work_attempts`, `lane_reports`, `broker_authority`, `work_queue` (new)
- **TS owns**: `sessions`, `broker_owned_bindings`, `conversation_model`, `deliveries`, `delivery_payloads`, `memory_files`
- **Shared**: `meta`, `schema_migrations` (Rust updates version after applying)

**Migration logic**:
```rust
// On startup, Rust supervisor:
if schema_version() < 1 {
  // Export existing 0.19 data
  export_to_json("work_attempts", ...);
  
  // Run v1 schema (auto-migration from v19 schema)
  apply_migration("v1.schema.sql", 19 → 1);
  
  // Restore data under new schema
  import_from_json("work_attempts", ...);
  
  // Mark as successful
  update_schema_version(1);
}
```

### 5.4 Migration Path (0.19 → 1.0.0)

**Phase 0: Preparation (week 1–2)**
- Rust supervisor code review + prototype IPC
- TS team refactors lane-governor, work-lane for IPC delegation
- Create data migration fixtures (0.19 database snapshots)

**Phase 1: Alpha (week 3)**
- Hybrid daemon runs with Rust supervisor as subprocess
- IPC validated against existing protocol
- Existing 0.19 tests pass with hybrid daemon

**Phase 2: Beta (week 4–5)**
- Release 1.0.0-rc with hybrid daemon
- User testing; catch edge cases in lane retirement, process cleanup
- Rust supervisor hardened based on feedback

**Phase 3: GA (week 6)**
- Release 1.0.0
- Publish migration guide: 0.19 → 1.0.0 (zero-downtime, automated data export/import)
- Publish upgrade runbook

**Data migration (automated)**:
```bash
# Export 0.19 database
gajaeway export-data --from /path/to/0.19/gateway.db --to /tmp/export.json

# Run Rust schema migration
gajaeway-supervisor init-schema --source /tmp/export.json \
  --db /path/to/1.0/gateway.db

# Verify
gajaeway ops census

# Cutover
systemctl stop gajaeway
mv /path/to/1.0/gateway.db /path/to/gateway.db
systemctl start gajaeway
```

## Part 7: Risk Analysis & Mitigation

### 7.1 Key Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Rust supervisor IPC deadlock/latency | Medium | High (blocks entire daemon) | Unit test IPC with chaos injection; timeout guards on all IPC calls |
| Schema migration data loss | Low | Critical | Export existing data before migration; validate row counts before/after |
| Broker rebinding race (session stranded) | Medium | Medium (user retries work) | Atomic session re-registration; test broker restart scenarios |
| Adapter incompatibility with new daemon | Low | High (service unavailable) | Backward-compatible protocol; existing adapters unchanged |
| Rust supervisor memory leak | Low | Medium (gradual degradation) | Memory profiling on long-running instances; bounded queue sizes |

### 7.2 Mitigation Strategies

1. **Rust supervisor testing**:
   - Unit tests for state machine (all transitions, edge cases)
   - Chaos tests: kill supervisor at random points during lane execution; verify database consistency
   - Stress test: create 1000s of lanes, simulate crashes, verify recovery
   - Integration test: hybrid daemon under existing test suite

2. **IPC reliability**:
   - Timeout on all IPC calls (default 30s, configurable)
   - Buffered queue between TS relay and Rust supervisor; no blocking
   - Explicit heartbeat if IPC silent for 5 min (indicates deadlock)

3. **Data migration safety**:
   - Export 0.19 database to JSON before schema migration
   - Validate: row counts, foreign keys, authority before cutover
   - Dry-run migration on test database first
   - Rollback procedure: revert binary, use old database

4. **Broker rebinding**:
   - Explicit test: start gateway, kill broker, restart broker, verify sessions re-attach
   - Timeout: if session cannot re-bind after 5 min, mark as failed and notify operator

## Part 9: Appendix: Schema Ownership & Migration Example

### Current Ownership (v0.19)

| Table | Owner | Rationale |
|---|---|---|
| `meta`, `schema_migrations` | Core | Infrastructure |
| `sessions`, `broker_owned_bindings`, `broker_tail_cursors`, `session_tail_cursors` | Bindings | Session state |
| `conversation_model` | Bindings | Per-session config |
| `deliveries`, `delivery_payloads` | Delivery | Outbound ledger |
| `broker_authority` | Core (singleton) | Authority proof |
| `work_attempts`, `lane_reports` | Work (orchestrator) | Lane execution |

### Proposed 1.0 Ownership

**Rust supervisor owns**:
- `work_attempts` (create, update, finalize)
- `lane_reports` (append-only activity log)
- `work_queue` (new: durable broker operation queue)
- `broker_authority` (read/verify; TS cannot mutate)
- `schema_migrations` (update version after running)

**TS relay owns**:
- Everything else
- Reads `work_attempts` for status (no write)
- Writes delivery, session state as before

### Migration Logic (0.19 → 1.0.0)

```
1. Supervisor reads 0.19 schema, detects version 19
2. Export all tables to JSON:
   - work_attempts, lane_reports (will be re-owned)
   - all others (will stay TS-owned)
3. Run v1.schema.sql (idempotent, creates new tables)
4. Restore exported data into v1 tables
5. Verify: row counts, foreign keys, authority
6. Mark schema_migrations.version = 1
7. TS relay continues to function with v1 schema
```

**No data loss**; existing lanes, sessions, deliveries all preserved.

## Conclusion

**Option B (Hybrid Core)** is the recommended path for Gajaeway 1.0. It achieves the reliability and durability guarantees needed for production while minimizing development risk and schedule impact. The Rust supervisor isolates the most failure-prone subsystem (work lane coordination) without requiring a wholesale rewrite. Post-1.0 evolution toward full Rust is possible and low-risk.
