## 2.2 `bound + operation_state_unknown` 무한 hold

### 증상

DM, channel, thread의 send가 `Control operation failed`로 끝난 후:

- DB: trigger `bound`
- GJC: operation `unknown`
- gateway: `recovery_hold ... operation_state_unknown` 무한 반복
- 새 메시지는 ghost turn에 steer되며 DB에서는 `done`

2026-09-05 재감사에서 playground-ko는 epoch 82 opRef `gw-p-35d920...`를 492회 hold했고, 이후 메시지 41개가 ghost turn에 붙어 있었다.

### 근본 원인

`bound`와 `accepted`를 지나치게 동일하게 보호했다. `bound`는 receipt가 없고, live session의 operation status가 unknown이며 queue가 empty/dead라면 send가 런타임에 귀속되지 않았다는 양성 증거다. 이를 무한 hold하면 origin 전체가 죽는다.

### 수정

- `920157c`: live reconcile에서도 unknown `bound`를 한 번 hold한 뒤 live+idle/dead 증거로 requeue/epoch 회전
- `accepted`는 이 휴리스틱으로 절대 재실행하지 않음
- `3b6ad5a`의 fresh tail boundary와 함께 stale output 귀속 방지

### 2026-09-05 운영 복구

- ghost session host PID `37367`만 종료
- broker inspect로 `live:false` 확인
- trigger + steer 46개를 pending으로 복원
- 새 epoch 84에서 재처리

주의: 수동 DB 복구는 반드시 old session을 먼저 non-live로 만든 뒤 해야 한다. queued follow-up이 나중에 살아나 중복 실행될 수 있기 때문이다.

## 2.4 AI final 생성 후 gateway silent drop

### 확정 재현

Trigger `그건 니가 알아야지`, steer `그런거까지ㅜ내가 해줘야돼?`:

- GJC final: 2026-09-04 14:22:17 KST
- 답변: `맞습니다 형님. 제가 알아봤어야 했습니다...`
- DB delivery row: 없음

### 근본 원인 1 — `turn_stream` capability skew

현재 GJC는 final을 다음 frame으로 보낸다.

```json
{
  "kind": "turn_stream",
  "phase": "finalized",
  "finalAnswer": true,
  "text": "...",
  "messageRef": "..."
}
```

Gateway decoder는 이를 unknown kind로 버렸다.

```text
unknown_runtime_event ... kind=turn_stream
```

수정: `67ad010`

- `phase=finalized && finalAnswer=true`만 assistant final
- live draft/reasoning은 delivery하지 않음

### 근본 원인 2 — fresh turn 전 historical `turn_stream` backfill

Tail attach 직후 이전 final들이 pre-receipt buffer에 들어가고, 새 send receipt 뒤 flush됐다. `turn_stream`에는 opRef/timestamp가 없어 이전 답이 새 turn 답으로 재사용됐다.

수정: `3b6ad5a`

- `TailHandle.beginTurn(opRef)`
- initial backfill을 fresh send 전에 폐기하고 cursor commit
- 경계 이후 fast/current frame만 receipt 후 flush
- restart recovery는 beginTurn을 호출하지 않아 current undelivered history를 보존

### 근본 원인 3 — transcript fallback

`transcript.list` 첫 페이지만 읽어 긴 session에서 최신 assistant를 찾지 못했다. continuation cursor는 connection-bound라 one-shot CLI를 넘겨 사용할 수도 없었다.

수정:

- `93a7fe4`: tail primary
- `28a75a2`: current turn이 terminal tail은 봤지만 assistant frame만 놓친 경우 `session.last_assistant`
- 모든 source 실패 시 empty text로 `done` 처리하지 않고 hold
- retired/status-only recovery에서는 unbounded last assistant 사용 금지

### 검증

- 연속 fresh turn `BOUNDARY ONE` → `BOUNDARY TWO`, 순서/본문 정확
- `TURN STREAM DELIVERY OK` 실제 Discord message까지 확인 후 삭제
- Discord API로 ledger confirmed text와 실제 message를 대조

4. `serve --session <id>`도 전체 list
5. `session tail <id>`도 전체 list
6. page traversal의 idempotency key도 충돌 가능

- `daa5b2ab51`: explicit serve는 exact lookup
- `eb8350efe4`: list traversal/page별 key 분리
- `9d2176a042`: explicit tail은 exact lookup

### Gateway 수정

## P0 — 다음 작업에서 반드시 처리

### P0-1. Session-host orphan reaper를 durable ownership 기반으로 수정

현재 `reapAgentDir`는 current broker PID의 직접 자식 위주로 찾는다. Broker가 죽어 reparent된 private `session-host-internal`은 누락될 수 있고, 오래 누적되면 cold-create readiness를 초과한다.

권장:

- private agent `session.list`/index의 PID + executable + stateRoot를 교차 검증
- 해당 private agent에 속한 dead/saved host만 종료
- 다른 `~/.gjc/agent`/worktree GJC process는 절대 건드리지 않음
- startup/periodic audit metric: indexed live, indexed dead, process exists but unindexed, private orphan count
- 100+ saved session soak test

### P0-2. Credential rotation을 session lifecycle에 연결

Provider 401/credential-invalid는 같은 session에서 retry해도 회복되지 않는다.

권장:

- structured 401/auth error를 `credential_epoch_stale`로 분류
- prompt 전: immediate epoch rotate
- prompt accepted 후: side effect 안전 규칙 유지, 새 입력만 fresh session으로 분리
- gateway config/launchd credential fingerprint (값 제외) 변경 감지 시 idle session proactive roll

### P0-3. Monitor failure detail을 `GjcCliError`로 뭉개지 말 것

DB에는 `dispatch phase failed ... GjcCliError/Error`만 남아 원인 추적에 transcript 직접 조회가 필요했다.

권장:

- secret-safe structured fields: `phase`, `sdkOperation`, `sdkCode`, `httpStatus`, `transportKind`, `sessionIdHash`, `opRef`
- raw prompt/response/token/path는 저장 금지
- `SessionTerminalError`에서 terminal status/error code를 보존

### P0-4. Monitor redrive/operator surface

## 8. 최종 판단

현재 snapshot에서는 chat, delivery, monitor, memory, GJC health가 모두 terminal/healthy 상태다. 그러나 이번 장애들은 “happy path 한 번 성공”으로 durability를 주장하면 안 된다는 것을 반복해서 증명했다.

가장 중요한 후속은 다음 세 가지다.

1. private orphan session-host를 ownership-safe하게 자동 정리
2. credential rotation/401을 session epoch lifecycle로 흡수
3. 200+ sessions / 반복 restart / 24h-equivalent cursor·monitor soak를 CI에 넣기

이 세 가지가 완료돼야 “한 번 launch하면 수년간 운용”이라는 목표를 강하게 주장할 수 있다.
